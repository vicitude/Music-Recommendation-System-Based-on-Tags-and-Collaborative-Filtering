# 项目阶段与标签、曲库重规划报告

日期：2026-11-08  
状态：讨论稿，仅用于确认范围；本报告不修改数据库、不导入数据、不替换现有标签。

## 一、结论摘要

当前项目不适合直接继续第 10 阶段实验或正式论文材料收口。原因不是推荐主链路没有实现，而是两个基础条件还不稳定：

1. 标签词库、歌曲标签和“时段/场景动态权重”的算法口径没有完全对齐。
2. 当前曲库规模较小，且导入依赖逐首人工填写，无法高效支撑后续模拟数据和实验。

建议暂时冻结第 10 阶段及真实业务验收，把下一轮工作改为“标签体系与曲库自动化基础建设”。这不会破坏已经完成的推荐、播放器、收藏、评分和实验框架，但标签类型、场景规则和自动导入完成后，需要重新生成模拟数据并重新跑实验。

## 三、标签体系重构方案

### 3.1 三个核心维度

#### 曲风：后台标准一级枚举，歌曲最多 2 个

采用调研得到的 27 个一级曲风：

流行、嘻哈说唱、电子、中国音乐、轻音乐、慢摇DJ、民谣、摇滚、国风、另类/独立、实验、民族歌曲、原声带、世界音乐、二次元、R&B、戏曲、古典、金属、新世纪、儿童、爵士、蓝调、乡村、雷鬼、拉丁音乐、放克。

当前词库中的“流行摇滚、民谣流行、乡村流行、电子舞曲、迪斯科、民族流行”等可以保留为曲风子类或兼容别名，但不应与一级枚举混在同一层。建议第一版先把它们迁移为“曲风子类”，不要删除历史名称。

“钢琴、管弦乐、原声、纯音乐、伴奏、混音版、氛围音乐”属于编制/版本/音频属性，不应继续冒充曲风。第一版可作为歌曲属性标签保留，后续再决定是否新增独立字段。

#### 情绪：后台标准枚举，歌曲最多 3 个

采用 15 个标准情绪：

狂欢、热血励志、活力、欢快、甜蜜、自信、浪漫、放松、治愈、思念、平静、孤独、悲伤、苦情、抑郁。

旧标签“伤感、忧郁、激昂、动感、热血、温柔”等不能直接物理删除。建议建立兼容映射：

| 旧标签 | 新标准标签 |
|---|---|
| 伤感 | 悲伤 |
| 忧郁 | 抑郁或孤独，需按候选置信度决定 |
| 激昂 | 热血励志 |
| 动感 | 活力 |
| 热血 | 热血励志 |
| 温柔 | 放松或甜蜜，不能无条件一对一替换 |
| 怀旧、释然、希望、梦幻、神秘、紧张 | 暂作为扩展情绪，不能强行伪装成 15 项标准情绪 |

#### 场景：后台标准枚举，歌曲最多 3 个

后台标准场景采用 11 个：

清晨、夜晚、助眠、学习、工作、运动、驾车、约会、小酒馆、KTV、游戏直播。

前台扩展场景不直接当作歌曲的第三套标准标签，而是作为用户选择或场景映射：

通勤、图书馆、咖啡厅、散步、旅行、独处、聚会、跑步、健身、阅读、冥想、午后。

建议映射关系：

| 前台扩展场景 | 后台标准场景 |
|---|---|
| 通勤 | 驾车、工作 |
| 图书馆 | 学习 |
| 咖啡厅 | 工作、放松 |
| 跑步、健身 | 运动 |
| 阅读 | 学习、助眠 |
| 冥想、独处 | 助眠、夜晚 |
| 聚会 | KTV、小酒馆、游戏直播 |
| 午后 | 工作、放松 |
| 旅行 | 驾车、工作 |

这样既能满足用户界面丰富性，又不会让算法面对一套无限膨胀、互相重叠的场景标签。

### 3.2 数据约束

标签数量限制应由后端统一校验，不能只靠前端：

- 每首歌曲：曲风最多 2 个、情绪最多 3 个、后台标准场景最多 3 个。
- 每个用户兴趣：继续允许选择 3—5 个，但三类标签合计不能超过 5 个。
- 标签推荐计算：只读取启用且已确认的歌曲标签。
- 自动生成的低置信度标签：进入候选区，不直接进入正式推荐。

### 3.3 替换而不是硬删除

不建议直接删除旧标签或直接改写历史 ID。推荐迁移顺序：

1. 扩充并冻结新词库。
2. 为旧标签建立 `legacy_name -> new_name` 兼容映射。
3. 批量迁移歌曲关系和用户兴趣关系，重复关系去重。
4. 对无法安全映射的旧标签保留为扩展标签，并标记待处理。
5. 重新生成 TF-IDF IDF、模拟用户画像和实验数据。
6. 观察一轮推荐结果后，再停用不再使用的旧标签；不直接物理删除。

## 四、按时段/场景动态权重方案

### 4.1 当前问题

当前实现只按 4 个时间段默认选择“通勤、运动、放松、夜晚”，场景命中率再间接调整三路权重。问题是：

- 时段粒度太粗。
- 10:00—17:00 全部归为运动，语义不合理。
- 清晨、学习、工作、助眠等场景无法自然地被时段命中。
- “时段动态”与“场景动态”没有清楚区分。

### 4.2 改造后的上下文优先级

```text
用户手动选择场景 > 用户历史偏好场景 > 当前时段默认场景 > 无场景
```

用户主动选择优先级最高；用户没有选择时，系统才按历史或时段推断。

### 4.3 建议 8 个时间段

| 时间 | 默认上下文 | 权重倾向 |
|---|---|---|
| 05:00—08:00 | 清晨 | 内容标签高，推荐平稳新鲜 |
| 08:00—10:00 | 通勤、驾车 | 内容与 Item-CF 平衡 |
| 10:00—12:00 | 工作、学习 | 内容高，减少无关热门 |
| 12:00—14:00 | 放松 | 内容与热门适度融合 |
| 14:00—17:00 | 工作、学习 | 内容与 User-CF 平衡 |
| 17:00—20:00 | 通勤、驾车、运动 | Item-CF 适度提高 |
| 20:00—23:00 | 放松、约会、小酒馆 | 内容与 Item-CF 平衡 |
| 23:00—05:00 | 夜晚、助眠 | 内容权重高，减少强刺激和重复热门 |

### 4.4 融合公式

保留三路推荐：标签内容、User-CF、Item-CF。令基础权重为 `w_content`、`w_user_cf`、`w_item_cf`，最终权重为：

```text
W_r = normalize(B_r × M_user(r) × M_scene(r) × M_time(r))
Score = W_content × Content
      + W_user_cf × UserCF
      + W_item_cf × ItemCF
```

其中：

- `B_r`：当前用户成熟度决定的基础权重，新用户偏内容，老用户逐步增加协同。
- `M_user`：用户主动选择或历史偏好对场景的匹配因子。
- `M_scene`：候选歌曲命中当前标准场景的比例。
- `M_time`：当前 8 档时段对推荐路由的调整因子。

用户手动场景的调整幅度应大于单纯时段默认值，避免系统自作主张覆盖用户意图。所有最终权重、场景来源、命中率和时段上下文都应写入每日快照和管理员诊断。

### 4.5 论文表述边界

可以写：

> 本系统根据用户成熟度、用户主动场景和当前时段，对标签内容过滤、User-CF 与 Item-CF 进行动态加权。

不能在没有真实实验前写：

> 该方法必然提升准确率、用户满意度或留存率。

正式实验应比较固定权重和动态权重的 Precision、Recall、Coverage、Diversity、Novelty，并使用模拟数据和真实内测数据分开报告。

## 五、自动导入与自动标注系统方案

### 5.1 目标

将“逐首打开后台、手填歌名、手填标签、手工发布”改为批量流水线：

```text
扫描音频目录
  → 音频指纹去重
  → 读取嵌入元数据
  → 文件名解析歌名/歌手/版本
  → 词库匹配标签候选
  → 可选音频特征分析
  → 置信度分级
  → 批量预览
  → 自动导入草稿
  → 高置信度自动发布 / 低置信度进入待处理队列
```

### 5.2 分层自动标注

#### 第一层：元数据和文件名规则，立即可做

- 读取 MP3/OGG/WAV 的标题、艺术家、专辑、时长、封面和格式。
- 解析常见文件名：`歌手 - 歌名`、`歌名 - 歌手`、括号版本、纯音乐、伴奏、Remix、Live 等。
- 用新词库和别名表匹配曲风、情绪、场景候选。
- 规则结果必须带 `basis`、`confidence` 和 `needs_review`。

#### 第二层：音频特征规则，可选增强

在不引入复杂深度学习前，可以提取 BPM、响度、能量、节拍稳定性、音频时长和是否有人声等特征，再用可解释规则给候选：

- 高 BPM、高能量：运动、跑步、舞曲、活力候选。
- 低能量、低响度、长持续音：放松、助眠、夜晚候选。
- 纯音乐、低人声特征：学习、工作、阅读候选。

这类结果只能是“候选标签”，不是音乐学事实；需要在页面展示依据和置信度。

#### 第三层：模型自动分类，后期选做

深度学习音频分类需要有带标签训练数据，当前不应作为自动导入的前置条件。后期有数据后，可独立增加模型版本、训练集、预测概率和人工纠正记录，不阻塞主系统。

### 5.3 自动导入分级策略

| 等级 | 条件 | 动作 |
|---|---|---|
| A | 元数据完整、指纹未重复、标签候选充分且无冲突 | 自动创建歌曲草稿，可按用户开关自动发布 |
| B | 歌曲信息完整但标签置信度一般 | 自动创建草稿并写入候选标签，不要求逐首编辑 |
| C | 歌手/歌名/时长缺失或标签冲突 | 进入异常队列，只处理异常项 |
| D | 指纹重复、文件损坏、格式不支持 | 跳过并报告原因 |

默认建议：A、B 自动导入为草稿；“自动发布”作为显式开关。当前你是学习项目，可开启批量自动发布，但必须保留导入批次和报告，便于撤回。

### 5.4 必须保留的审计信息

每个导入批次记录：

- 批次 ID、导入目录、执行时间、生成器版本。
- 原始文件名、SHA-256、大小、格式、时长。
- 元数据来源和解析结果。
- 每个标签候选的来源、置信度、依据和最终状态。
- 导入结果：草稿、已发布、跳过、失败。
- 是否允许播放由批量导入开关决定，不把自动导入等同于版权许可。

### 5.5 与现有系统的关系

当前系统已经有：

- 本地目录清单扫描。
- 元数据规范化。
- 文件名规则候选标签生成。
- 草稿导入和本地音频关联入口。
- 管理员标签确认和歌曲发布按钮。

当前缺少：

- 新标签体系的统一词库和别名映射。
- 批量导入任务和批次状态。
- A/B/C/D 置信度分级。
- 批量自动发布开关和可撤回批次。
- 只展示异常项的处理页面。
- 音频特征候选标注。
- 导入完成后的汇总报告和错误重试。
