# 标签体系与自动曲库实施计划

日期：2026-11-08  
状态：截至2026-11-09，A1—A3/B1完成；B2多片段/映射/拒识及批次候选展示已实现，后端359项、工具11项通过。三首真实样本全部拒识，标签质量未闭环，B3待做。详见decisions/054-v54-clap-multisegment-batch-candidates.md。

## 一、总体目标

本轮不继续堆叠实验图表，而是先解决推荐系统的两个基础问题：

1. 标签体系要稳定、可解释，并能支撑“按时段/场景动态调节融合权重”。
2. 曲库导入要批量化，自动提取元数据和音频特征，自动生成标签候选，避免逐首手工填写。

本轮完成后，系统应形成如下链路：

```text
音频目录
  → 批量扫描与指纹去重
  → 元数据/文件名解析
  → 音频特征分析
  → 自动标签候选与置信度
  → 批量导入草稿
  → 可选自动发布
  → 标签内容 + 协同过滤 + 时段/场景动态融合
```

## 二、已确认的标签口径

### 2.1 曲风标签

采用 27 个后台标准一级曲风，歌曲最多选择 2 个：

流行、嘻哈说唱、电子、中国音乐、轻音乐、慢摇DJ、民谣、摇滚、国风、另类/独立、实验、民族歌曲、原声带、世界音乐、二次元、R&B、戏曲、古典、金属、新世纪、儿童、爵士、蓝调、乡村、雷鬼、拉丁音乐、放克。

现有的流行摇滚、民谣流行、乡村流行、电子舞曲等作为子类或兼容别名保存，不与一级曲风混为同一层。钢琴、管弦乐、纯音乐、伴奏、混音版等暂作为音频属性/版本候选，不直接计入一级曲风。

### 2.2 情绪标签

采用 15 个标准情绪，歌曲最多选择 3 个：

狂欢、热血励志、活力、欢快、甜蜜、自信、浪漫、放松、治愈、思念、平静、孤独、悲伤、苦情、抑郁。

旧标签不直接删除，先通过兼容映射迁移。例如：伤感 → 悲伤，激昂/热血 → 热血励志，动感 → 活力。无法可靠一对一映射的标签进入扩展或待处理状态。

### 2.3 后台标准场景

歌曲最多选择 3 个后台标准场景：

清晨、夜晚、助眠、学习、工作、运动、驾车、约会、小酒馆、KTV、游戏直播。

自动标注第一版只对其中具有较强声学依据的场景输出候选：运动、助眠、放松、学习、工作、驾车。约会、小酒馆、KTV、游戏直播等保留为用户场景或规则映射，不宣称能够仅凭音频准确识别。

### 2.4 前台扩展场景

前台可以提供通勤、图书馆、咖啡厅、散步、旅行、独处、聚会、跑步、健身、阅读、冥想、午后等选择，但这些是用户使用场景，不直接作为歌曲自动标签。

### 2.5 时间上下文

时间上下文不是歌曲永久标签，而是推荐计算时动态生成的上下文。固定为 8 档：

| 时间 | 上下文 | 默认关联场景 |
|---|---|---|
| 00:00—05:00 | 凌晨 | 助眠、夜晚、独处 |
| 05:00—08:00 | 清晨 | 清晨、放松、运动 |
| 08:00—11:00 | 上午 | 工作、学习 |
| 11:00—14:00 | 午间 | 放松、工作 |
| 14:00—17:00 | 下午 | 工作、学习 |
| 17:00—20:00 | 傍晚 | 通勤、驾车、运动 |
| 20:00—23:00 | 夜晚 | 放松、约会、小酒馆 |
| 23:00—24:00 | 深夜 | 夜晚、助眠、独处 |

上下文优先级固定为：

```text
用户手动场景 > 用户历史偏好场景 > 当前时间上下文 > 无场景兜底
```

## 四、阶段详细计划

### A0：现状冻结与数据盘点

**目的**：避免误删、误迁移和误把旧模拟数据当作新数据。

**工作内容**：

- 读取当前数据库中的标签总数、按类型数量、歌曲标签关系和用户兴趣关系。
- 统计旧标签是否已经被写入真实专用库。
- 统计 `origin=SIMULATED` 的账号数量；若已存在，只做隔离和备份记录，不立即删除。
- 输出旧标签到新标签的迁移候选表。
- 固化当前推荐测试基线。

**验收条件**：

- 有一份脱敏的标签与关系统计。
- 确认旧模拟账号是否已实际导入。
- 未修改歌曲、用户、标签和媒体数据。

### A1：新标签词库与兼容映射

**目的**：建立新体系，同时保证旧代码和旧数据不会立即失效。

**工作内容**：

- 重写标签库为曲风、情绪、后台标准场景三组。
- 增加标签说明、别名、是否可自动识别、是否允许作为歌曲标签等元信息。
- 建立旧标签兼容映射，不直接删除旧标签。
- 明确时间上下文不写入 `SongTag`，而作为推荐上下文配置。

**重点影响范围**：

- `backend/music/tag_library.py`
- `Tag`、`SongTag`、`UserTag` 的读取和管理逻辑
- 本地歌曲候选标签生成器
- 前台标签展示与兴趣选择
- 推荐算法中的标签 ID 和场景名称
- 现有模拟用户画像生成器

**验收条件**：

- 新词库可导入。
- 旧标签关系仍可读取。
- 新旧名称不会产生同类重复关系。
- 推荐读取只使用启用且允许参与推荐的标签。

### A2：标签约束与管理界面

**目的**：从数据层保证标签数量和类别正确，不能只靠人工记忆。

**工作内容**：

- 后端校验每首歌曲最多 2 个曲风、3 个情绪、3 个后台场景。
- 前端编辑页面按维度分组展示，并显示剩余可选数量。
- 重复标签、旧标签和扩展场景显示清楚。
- 标签超限时阻止保存并给出中文提示。
- 批量导入也复用同一套校验。

**验收条件**：

- 后端直接请求超限会失败。
- 后台手动编辑和批量导入使用同一规则。
- 现有歌曲标签不会因为页面改版被静默删除。

### A3：时间上下文与动态权重

**目的**：落实任务书中的“按时段/场景动态调节融合权重”。

**工作内容**：

- 将原 4 档时间映射改为 8 档。
- 增加时间上下文名称、区间、默认场景和权重调整因子。
- 保留三路推荐：Content、User-CF、Item-CF。
- 计算基础用户成熟度权重，再叠加时间因子、用户场景因子和歌曲场景命中率。
- 最终权重归一化为 1。
- 每日快照和管理员诊断记录时间上下文、场景来源、匹配率和最终权重。
- 推荐解释能说明“因为当前是深夜/你选择了运动场景”等上下文依据。

**建议公式**：

```text
W_r = normalize(B_r × M_user(r) × M_scene(r) × M_time(r))
Score = W_content × Content
      + W_user_cf × UserCF
      + W_item_cf × ItemCF
```

**验收条件**：

- 8 个时间段边界测试通过。
- 手动场景优先于时间默认场景。
- 无场景时保持安全回退。
- 同一用户、同一歌曲、不同时间上下文可以产生不同有效权重。
- 解释和诊断与实际权重一致。

### B1：自动导入基础流水线

**目的**：从逐首导入改为按目录批量导入。

**工作内容**：

- 扫描 MP3、WAV、OGG 文件。
- 读取标题、歌手、专辑、时长、封面检出状态和格式；B1不保存封面图片。
- 解析常见文件名格式和版本词。
- 计算 SHA-256，发现重复文件时跳过。
- 将文件复制到项目媒体目录，不直接把源目录当作系统媒体目录。
- 创建导入批次和每首歌曲的结果记录。
- 默认导入为草稿，不自动发布；明确确认后才复制音频并写入，批量发布开关统一在B3实现。

**验收条件**：

- 一次导入几十或几百首不会要求逐首打开编辑页。
- 重复导入不会创建重复歌曲或重复媒体。
- 每首失败都有原因。
- 原始目录不被修改。

### B2：自动标签候选系统

**目的**：让程序先完成大部分标签工作，用户只处理异常项。

**第一版输入**：

- 文件名和嵌入元数据。
- 音频时长、BPM、响度、能量、频谱、人声/纯音乐倾向等特征。
- 新标签词库、别名和规则。

**第一版输出**：

- 曲风候选及置信度。
- 情绪候选及置信度。
- 音频适配场景候选及置信度。
- 证据来源和规则说明。

**置信度策略**：

- `>= 0.75`：高置信度，可按开关自动写入。
- `0.55—0.75`：中置信度，写入候选区，不直接进入正式推荐。
- `< 0.55`：忽略。
- 每首曲风最多 2 个、情绪最多 3 个、场景最多 3 个。

**深度学习模型**：

- 不作为第一版前置条件。
- 先用可解释规则和音频特征完成可运行版本。
- 后续可接入 Essentia、Musicnn、MERT 或 CLAP，作为独立模型版本。
- 模型输出必须保留概率和版本，不直接覆盖人工确认标签。

**验收条件**：

- 自动标签可追溯到文件名、元数据、音频特征或模型概率。
- 低置信度不被伪装为确定标签。
- 没有候选时允许留空，不强行贴标签。

### B3：批量发布、报告与异常队列

**目的**：让用户只处理真正需要人的部分。

| 等级 | 处理方式 |
|---|---|
| A | 元数据完整、指纹唯一、标签候选充分：自动创建草稿，可选自动发布 |
| B | 信息完整但标签置信度一般：自动创建草稿，进入候选区 |
| C | 歌手/歌名/时长缺失或标签冲突：进入异常队列 |
| D | 文件损坏、格式不支持或指纹重复：跳过并记录原因 |

**工作内容**：

- 批次汇总：成功、草稿、发布、跳过、失败、待处理数量。
- 只显示 C 类异常和用户主动筛选的 B 类候选。
- 允许批量确认、批量拒绝和失败重试。
- 批量自动发布必须单独确认，不默认打开。
- 保留批次撤回边界，至少可以批量下架本批次发布的歌曲。

**验收条件**：

- 40 首扩展到 100—500 首时，用户不需要逐首填写。
- 用户只处理异常项。
- 可通过批次号追踪和回滚发布状态。

### C1：新标签下重建模拟数据

**目的**：让模拟用户画像和新标签体系一致。

**工作内容**：

- 不自动删除旧模拟账号；先统计并等待清理确认。
- 确认后仅清理 `origin=SIMULATED` 的账号及其级联关系。
- 重新生成 200 个有差异的用户画像。
- 行为偏好使用新曲风、情绪和场景标签。
- 为不同时间上下文生成可用于动态权重测试的行为时间分布。

**验收条件**：

- 真实账号、歌曲和媒体不受影响。
- 200 个模拟用户均有明确画像差异。
- 模拟行为能同时触发内容、User-CF 和 Item-CF。

### C2：模拟实验与看板更新

**工作内容**：

- 重新导出模拟数据集。
- 重新运行 HOT、CONTENT、USER_CF、ITEM_CF、FIXED、ADAPTIVE 对比。
- 增加固定时间上下文与动态时间上下文对比。
- 观察 Precision、Recall、NDCG、Coverage、Diversity、Novelty。
- 更新看板数据和说明，继续标记 `SIMULATED_SELF_TEST`。

**验收条件**：

- 报告中明确标签版本、词库版本、时间规则版本和随机种子。
- 不把模拟结果写成真实用户提升。

### D1：恢复真实业务验收

在 A、B、C 阶段稳定后恢复：

- 专用 MySQL 迁移与数据范围核验。
- 批量导入有权使用的音频。
- 前台真实播放、收藏、评分、场景切换。
- 管理员诊断和导入批次验收。

### D2：恢复正式实验与论文材料

在真实内测数据或合法研究数据到位后恢复：

- 时间切分和防泄漏检查。
- 固定权重与动态权重对比。
- 真实实验表格和论文图表。
- ER 图、系统架构图、推荐流程图和答辩演示脚本。

## 五、暂停与继续规则

- 阶段 9、阶段 10暂时暂停，不删除已有代码和看板。
- A0—A3完成前，不导入新一批模拟用户，不跑正式实验结论。
- B1—B3完成前，不继续人工逐首导入大批歌曲。
- C1清理旧模拟账号前，必须单独确认，禁止自动删除。
- 任何新依赖（如 `librosa`、`essentia`、模型包）先检查本机环境并单独确认安装。
- 真实 MySQL 写入、真实媒体复制和批量发布继续遵守原有确认门槛。
